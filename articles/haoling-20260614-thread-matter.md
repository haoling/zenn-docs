## Threadってなんですか、という話

少し前置きが要るので整理しておきます

**Thread**は省電力メッシュの無線規格です。「ルーターのない無線LAN」というイメージが近いかもしれない。ただ、WiFiルーターに相当する「外のネットワークへの出口」がなければ、Threadの中で閉じたネットワークしか構築できません。一般的な「IPレイヤーのイーサネット」に接続するためにはプロトコル変換をしてくれる出入り口が必要で、それが **Thread Border Router（OTBR）** の役割です。ルーターのないWiFiがただのイーサネットでしかないように、OTBRのないThreadは外部連携のできないただのメッシュです

さらに、Threadが「通信手段」だとすると、「ボタンを押したら電気をつける」みたいなオートメーションを実現するのは**Matter**というプロトコルの仕事です。ThreadはMatterが走る土台に過ぎない

つまり今回は：

- **Thread** → ボタンとの無線通信手段
- **OTBR** → ThreadとLANの橋渡し
- **matter-server** → Matterデバイスをコントロールする
- **Home Assistant** → オートメーションを組む

という構成を組みました

## 前半：意外とすんなり動いた（と思った）

ESP32-C6はWiFiもThreadもしゃべれます。ならばこれ1枚でOTBRを動かせるのでは？

espressifがOTBR実装を公開していたので、ビルドして書き込みました。動きました。Threadネットワークが立ち上がり、OTBRとしてLANに接続されました

matter-serverはKubernetesの中に立てることにしました。MatterサーバーはThreadデバイスと直接無線通信する必要はなく、OTBRとIPで話せればいい。k8sに閉じ込めても問題ないはずです

ここで最初の壁がきます

**うちのk8sはIPv6未対応でした。**

これが問題なのは、matter-serverがThreadデバイスと会話するためにIPv6を必須とするためです。IPv6のパケットをほかのセグメントにルーティングすることはできるけど、IPv6のパケットをIPv4のネットワークにルーティングすることはできないのです

対策として、matter-serverのPodに仮想的な2枚目のNICを追加して（Multusというk8sの機能を使った）、そのNICをLANに直接露出させました。matter-serverがOTBRと直接L2でしゃべれる状態にしたわけです

これ自体はうまくいったんですが、またしても壁がきました

LinuxのIPv6まわりの設定では、**OTBRが広告しているThread内部の経路情報を、デフォルトでは受け取ってくれない**んですね。つまりmatter-serverのPodは「そのIPv6アドレスはどこに送ればいい？」を知らない状態です

ボーダールーターにパケットが届かない＝ボーダールーターの先にあるThreadデバイスにパケットが届かないので、ThreadデバイスとのMatterセッションが確立できず、タイムアウトし続けます

最終的には、matter-serverのIPv6ルーティングテーブルに、OTBRへの経路を直接書いてしまう方法で解決しました。OTBRが管理しているThreadのユニークローカル/64セグメントへのGatewayとしてOTBRのリンクローカルアドレスを指定したわけです。これで疎通できて、BILRESAがHomeAssistantに現れてボタンの動作も確認できました

なるほど、電池の電圧も取れるし、ファームウェアのバージョンも取れるんだ、ふーん

## 後半：翌日、崩壊

翌日、意気揚々とHomeAssistantを確認したら、BILRESAが「利用不可」になっていました、なんでや

あれこれ調べると、どうやら**ESP32-C6のWiFiスタックとThreadスタックを同時に動かすのは、CPUとメモリ的に結構つらい**らしい。前日は動いて見えたものの、じわじわ不安定になっていたようです

1枚で全部やらせるのは無理があったようだ・・・

良いでしょう、方針を変えましょう。ESP32-C6はThreadラジオ専用の **RCP（Radio Co-Processor）** に徹させて、OTBRの頭脳部分は別のLinuxマシンに任せる構成にしよう。ちょうどUbuntuが動いているN100のミニPCがあったので、そこでOTBRをPodmanコンテナとして動かせばよかろう

移行作業の前に、現在のThreadネットワークのデータセット（ネットワーク認証情報や設定一式）をバックアップしておく必要があります。OTBRを作り直すとネットワーク設定が変わるので、バックアップを取っておくとデバイスの再ペアリングを避けられる可能性があります

N100でOTBRが起動したのは良かったんですが、またひとつ詰まるポイントがありまして。

**XIAO ESP32-C6はUSBシリアル変換チップを使っておらず、USB CDCで直接通信する方式**なんですね。RCPのファームウェアをビルドする際に `CONFIG_OPENTHREAD_RCP_USB_SERIAL_JTAG=y` を設定しておかないと、ホスト側のLinuxからシリアルデバイスとして認識されません

そしてもう一個。matter-serverとの間のIPv6経路問題が、**また起きました。**

OTBRが変わったのでThreadメッシュのアドレスも変わっています。前回と同じように経路を追加して疎通を回復し、BILRESAを再ペアリングして、ボタンが動くことを確認しました

ESP32-C6単体のOTBRのときにActive Operational Dataset（TLVバイナリ）を取得しておいて、新しいOTBRに同じTLVを設定したんだけど、どうにもユニークローカル/64セグメントが変わってるんだよなぁ・・・わからん

とりあえず。ハプニングはあったものの、今度こそ、安定して動いています

## 学んだこと：IPv6のスコープを意識する

IPv6にはいくつかのアドレス種別があって、それぞれ「届く範囲（スコープ）」が違う

- **グローバルユニキャストアドレス**：インターネット全体で有効（`2001:` や `240b:` など）
- **リンクローカルアドレス**：同じL2セグメント内だけで有効（`fe80::` から始まる）
- **ULA（ユニークローカルアドレス）**：プライベートIPv6。組織内ネットワークで有効（`fd00::` から始まる）

違うセグメント同士はルーティングしてやらなければならない。当たり前の話だけれど、IPv4では「ドットが3つ」だったのに対してIPv6では最大でコロンが7個あり、16bitで区切られている。これが16bit単位ならわかりやすいんだけど、平気で/56とか/60とかで区切ってきたりする

たとえばv6プラスを関東圏で契約すると、ひかり電話ありの場合 240b:11:XXXX:YY00::/56 がHGWに割り当てられ

```
240b:0011:a384:ab | cd:0000:8a2e:0370:7334
←──── /56 ───────→ ←──── ホスト部 ────────→
```

そこから 240b:11:XXXX:YYf0::/60 がDHCPv6-PDで払い出されて

```
240b:0011:a384:abc | d:0000:8a2e:0370:7334
←──── /60 ────────→ ←────── ホスト部 ─────→
```

そこからさらにルータが 240b:11:XXXX:YYf1::/64 というセグメントを切り出してLAN側に配布したりする

```
240b:0011:a384:abcd: | 0000:8a2e:0370:7334
←──── /64 ──────────→ ←──── ホスト部 ─────→
```

これに慣れていなくて、k8sのクラスタ内部 - kube-proxy - 物理LAN - Threadボーダールーター - Threadメッシュ - Threadデバイス、という経路で、それぞれどこでルーティングが必要になるのか、直感的に理解できなかったことが、今回のハマりポイントと言える
